# 실무·제품 설계 기능 후보

아래 항목은 모두 [[source-2026-09-06-product-proposals|제품 제안 대화]]에서 나온 **추가 후보**다. 기대 효과는 설계 판단이며 구현 완료나 사용자 검증을 뜻하지 않는다. 기존 기능은 [[onputer-product|제품 개요]]와 구분해 읽는다.

## 실무 효용 후보

| 후보 | 사용 장면 | 필요한 변화와 경계 |
|---|---|---|
| 작업 이력과 실행 목록 | “아까 돌린 작업 어디까지 됐어?” | 작업명·상태·로그·결과를 남긴다. process_id 없이도 찾고 재시작 뒤 기록을 조회한다. |
| 작업 전 체크포인트와 복원 | “방금 수정한 것만 취소해줘” | 패치 적용 실패 시 복원과 달리, 나중에 특정 작업의 변경을 취소한다. 기존 사용자 변경과 Git 미커밋 변경을 보존한다. |
| 프로젝트별 검증 절차 | “프로젝트 규칙대로 테스트하고 결과 알려줘” | 현재 분석의 명령 후보를 저장된 테스트·타입 검사·빌드 절차에 연결하고 실행 결과를 모은다. |
| 환경 진단 | “이 PC에서 왜 실행이 안 되는지 찾아줘” | Node·Python·Git·가상환경·포트·PowerShell을 함께 진단한다. Windows 시행착오 감소가 목표다. |
| 긴 로그의 핵심 오류 추출 | “결국 뭐가 실패한 거야?” | 실패 명령·종료 코드·오류 주변을 먼저 보여주고 전체 로그도 보관한다. |

## 제품 구조 후보

| 후보 | 설계 방향 | 후속 기능과의 관계 |
|---|---|---|
| 작업 단위 도입 | 요청에 작업 ID를 부여하고 명령·파일 변경·테스트·결과를 연결 | 이력·재개·복원의 공통 기반 |
| 기본 기능과 선택 확장 분리 | 파일·코드·프로세스는 기본, 브라우저·문서·이미지는 선택 설치 | 가벼움 유지와 코딩 외 업무 확장을 함께 검토 |
| 연결별 프로젝트·권한 설정 | 연결마다 프로젝트와 읽기·쓰기·명령 실행 권한 지정 | 하나의 토큰으로 작업공간을 공유하는 구조의 운영 편의 개선 |
| 검증된 연결 방식 제공 | 우선 웹 서비스 하나의 인증·터널·연결 절차 완성 | 사용자가 따라 할 수 있는 첫 연결 경험 |

## 기능 설계에서 지킬 경계

파일 복원은 외부 효과 취소와 다르다. 이미 푸시한 결과나 외부 서비스 요청까지 모두 되돌린다고 약속하지 않는다.

읽기 전용은 파일 쓰기와 명령 실행을 실제로 차단해야 한다. 명령을 실행할 수 있는 상태를 OS 수준으로 격리됐다고 표시하면 안 된다.

자체 AI 모델·복잡한 에이전트 실행 엔진은 당분간 보류하자는 제안이다. 판단을 연결 AI에 두고 onputer가 실행·기록·검증을 담당하도록 역할을 유지한다.

## 후보 사이의 관계

환경 진단은 작업을 시작할 수 있는지, 검증 절차는 결과가 기준을 만족하는지, 오류 로그는 실패 이유가 무엇인지에 각각 초점을 둔다. 이력은 이 세 과정을 작업 단위에 연결하고, 복원은 그중 파일 변경에만 적용 범위를 명시하는 방식으로 함께 설계할 수 있다. 이는 위 후보들을 묶는 설계 해석이며 확정된 구현 구조가 아니다.
