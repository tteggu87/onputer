# onputer 제품 확장 제안 대화 기록

작성일: 2026-09-06. 출처: onputer 개발 대화에서 사용자가 요청한 네 관점의 제품 제안과 그 답변.
이 파일은 해당 기획 내용을 Markdown 구조로 옮긴 고정 입력이다. 전체 개발 대화의 전사나 외부 사용자 조사 결과가 아니다.
문서화 요청은 있었지만 아래 추가 기능 전체의 구현 승인, 일정 확정, 효과 검증을 뜻하지 않는다.

## 1. 제품 방향과 현재 기반

사용자는 간단하고 효과적인 Streamable HTTP MCP를 통해 웹 채팅에서 컴퓨터 작업을 수행하는 onputer를 원한다. 주 작업 환경은 Windows이고 macOS 실행도 지원한다. 기존 CodexPro와 독립된 폴더와 공개 저장소를 사용한다.
제안 시점의 onputer는 v0.2.0, Git 커밋 f546732a63b2ba7bed17daeb373f8a7e8b810704이다. 범용 도구 19개로 작업공간, 파일 검색·읽기·편집, 여러 파일 패치, 코드 구조·참조·변경 영향 분석, Git 변경 확인, 비동기 명령·출력·중단, AGENTS.md·스킬 읽기를 제공한다.
19개 도구를 더 늘리는 것 자체보다 작업을 맡기고 진행 상황과 결과를 확인하며 필요하면 되돌리는 경험을 완성하는 것이 제안의 중심이다.
현재 작업 기록은 메모리에 있고 재시작하면 사라진다. 실행 조회에는 process_id가 필요하다. 별도 실행 목록과 결과물 전달 화면은 아직 없다. 외부 HTTPS 연결은 별도 터널 설정이 필요하다.

## 2. 실무 관점

| 후보 | 사용 장면 | 제안 이유 |
|---|---|---|
| 작업 이력과 실행 목록 | 아까 돌린 작업 어디까지 됐어? | 작업명·상태·로그·결과를 남기고 process_id를 잃어도 찾게 한다. 재시작 뒤 기록이 남아야 한다. |
| 작업 전 체크포인트와 복원 | 방금 수정한 것만 취소해줘 | 현재 패치 오류 복원과 구분되는 사용자 요청에 따른 나중 복원이다. Git 미커밋 변경과 기존 사용자 변경을 보존해야 한다. |
| 프로젝트별 검증 절차 | 이 프로젝트 규칙대로 테스트하고 결과 알려줘 | 현재 분석이 알려주는 후보 명령을 프로젝트에 저장된 테스트·타입 검사·빌드 절차와 연결하고 결과를 모은다. |
| 환경 진단 | 이 PC에서 왜 실행이 안 되는지 찾아줘 | Node·Python·Git·가상환경·포트·PowerShell 문제를 함께 확인해 Windows 시행착오를 줄이는 것을 목표로 한다. |
| 긴 로그의 핵심 오류 추출 | 출력은 많은데 결국 뭐가 실패한 거야? | 실패 명령·종료 코드·오류 주변 내용을 먼저 보여주고 전체 로그도 보관한다. |

파일 변경은 복원할 수 있지만 이미 푸시했거나 외부 서비스에 요청한 효과까지 모두 되돌린다고 약속해서는 안 된다. 이러한 범위 구분은 체크포인트 기능의 전제다.

## 3. 프로덕트 설계 관점

| 후보 | 설계 방향 | 기대 효과 |
|---|---|---|
| 작업 단위 도입 | 요청 하나에 작업 ID를 부여하고 명령·파일 변경·테스트·결과를 연결 | 별도 도구들을 하나의 업무로 묶고 이력·재개·복원의 공통 기반으로 사용 |
| 기본 기능과 선택 확장 분리 | 기본은 파일·코드·프로세스, 브라우저·문서·이미지는 선택 설치 | 가벼움을 유지하며 코딩 외 업무로 확장 |
| 연결별 프로젝트·권한 설정 | 연결마다 허용 프로젝트와 읽기·쓰기·명령 실행 여부 지정 | 하나의 토큰으로 모든 작업공간을 공유하는 현재 구조의 운영 편의 개선 |
| 검증된 연결 방식 제공 | 실제 사용할 웹 서비스 하나의 인증·터널·연결 절차부터 완성 | MCP 지원이라는 설명을 사용자가 따라 할 수 있는 연결 경험으로 전환 |

읽기 전용 모드는 파일 쓰기와 명령 실행을 실제로 차단해야 한다. 명령을 허용한 상태를 작업공간 안에 격리됐다고 표현해서는 안 된다.
자체 AI 모델이나 복잡한 에이전트 실행 엔진을 onputer에 넣는 것은 당분간 보류한다는 제안이다. 판단은 연결한 채팅 AI가 하고 onputer는 실행·기록·검증을 정확하게 담당한다.

## 4. 사용자 관점

| 후보 | 사용 경험 |
|---|---|
| 작은 로컬 관리 화면 | 프로젝트 선택, 서버 시작·중지, 연결 주소 복사, 현재 작업 확인을 한 화면에서 처리 |
| 단계별 연결 진단 | 서버 실행됨 → 외부 주소 연결됨 → 인증 성공 → 실제 도구 호출 성공을 각각 표시 |
| Windows 트레이 아이콘 | 창을 닫아도 상태를 확인하고 일시 중지·종료·관리 화면 열기 |
| 결과물 열기·미리보기·다운로드 | 파일을 만들었다는 설명과 함께 실제 결과를 열거나 받기 |
| 필요할 때만 지침 안내 | 새 폴더의 AGENTS.md나 변경된 지침을 발견하면 AI에 전달하고 이미 전달한 내용 반복은 줄이기 |

결과물 전달은 특히 가치가 높다는 판단이다. 파일 생성 후 사용자가 파일을 찾는 단계가 남으므로 CSV 정리·보고서 생성·이미지 변환 업무에서 결과를 바로 확인하고 받는 경험을 제공한다.
MCP는 이미지와 리소스 링크를 지원하지만 실제 표시·다운로드 방식은 연결할 웹 서비스에서 확인해야 한다. 모든 서비스에서 같은 UI를 제공한다고 약속하지 않는다.

## 5. 우와 경험

새 채팅에서도 어제 하던 일을 이어간다: “어제 보고서 정리하던 것 이어서 해줘.” 이전 목표·변경 파일·성공과 실패 명령·남은 일을 전달하고 현재 파일이 달라졌는지도 확인한다. 대화 전체 저장보다 작업 기록과 현재 파일 상태를 연결하는 것이 핵심이다. 서버 재시작 뒤 종료된 프로세스를 무조건 다시 실행하면 안 된다.

무엇을 했는지 근거가 붙은 결과를 받는다: “파일 4개 수정, 테스트 12개 통과, 결과 보고서 생성. 변경 보기 / 결과 열기 / 파일 변경 되돌리기.” 이 숫자는 화면 경험을 설명하는 예시이지 측정 결과가 아니다. 도구 호출마다 큰 카드를 띄우기보다 작업이 끝날 때 한 번 정리된 결과 화면을 보여주며 조용한 출력을 유지한다.

화면을 고치고 바뀐 화면까지 보여준다: “버튼 정렬 수정하고 전후 화면 보여줘.” 코드 수정 → 개발 서버 실행 → 페이지 확인 → 스크린샷 비교로 연결한다. 브라우저 설치와 실행 관리가 추가되므로 선택 확장으로 두는 제안이다.

매주 하던 작업이 다시 실행 가능한 절차가 된다: “지난번 방식대로 이번 주 CSV도 정리해줘.” 입력 폴더·실행 절차·결과 위치·검증 방법을 저장해 입력만 바꿔 재사용한다. 예약 실행부터 만들기보다 검토된 절차를 사용자가 다시 실행하는 기능부터 시작한다.

## 6. CodexPro에서 참고할 것과 보류할 것

참고할 항목은 연결 진단·설정 흐름, 계획·상태·결정 기록 방식, 도구·쓰기·실행 모드 구분이다. Codex 전용 인계 기능을 그대로 늘리기보다 onputer 작업 이력에 활용하고 권한 설정도 간단하고 명확하게 재설계한다.
여러 터널 제공자 전체 지원, Codex 대화 기록 읽기, 매 호출 HTML 카드를 모두 가져올 필요성은 낮다는 판단이다. 이들은 확정 폐기 사항이 아니라 현재 우선순위가 낮은 후보다.

## 7. 구현 순서와 완료 기준

| 순서 제안 | 묶음 | 완료 판단 기준 |
|---|---|---|
| 1 | 연결 설정 + 로컬 관리 화면 | 새 Windows PC에서 문서를 뒤지지 않고 첫 도구 호출까지 성공 |
| 2 | 작업 이력 + 결과 요약 + 로그 보관 | 채팅을 바꿔도 무엇이 실행됐고 왜 실패했는지 확인 가능 |
| 3 | 체크포인트 + 파일 변경 복원 | 기존 사용자 변경을 보존하면서 특정 작업의 변경만 취소 가능 |
| 4 | 결과물 미리보기·다운로드 | 생성한 파일을 채팅에서 확인하고 가져갈 수 있음 |
| 5 | 작업 재개 + 반복 절차 | 실제 반복 업무 하나를 다음 날에도 재사용 가능 |

이 순서는 제안이며 확정 일정이나 납기 약속이 아니다. 작업 단위와 기록 모델은 여러 후속 기능이 공유하는 기반이다.

## 8. 우선 제안 묶음과 남은 판단

당장 하나의 제품 개선 묶음을 고르면 연결 관리 화면 + 작업 이력 + 최종 결과 보기를 추천한다. 도구를 새로 배우지 않아도 무엇을 하고 있는지 알게 하고 기존 19개 도구의 가치를 드러내려는 목적이다.
실무적으로는 이력·검증·환경 진단·파일 복원, 사용자 경험에서는 쉬운 연결·진행 상황·결과물 전달, 우와 경험에서는 새 채팅 재개·근거가 붙은 결과·수정 전후 미리보기를 강조한다.
기대 효과는 설계 판단이며 사용자 실험으로 검증되지 않았다. 첫 연결 대상 웹 서비스, 대표 실무 작업, 각 기능의 범위, 개발 일정과 구체적인 측정 기준은 아직 결정하지 않았다.
